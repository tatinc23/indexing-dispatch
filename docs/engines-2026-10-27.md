## 1. IndexNow

Sources: https://www.indexnow.org/documentation, https://www.indexnow.org/faq, https://www.indexnow.org/terms,
https://www.indexnow.org/searchengines.json, per-engine `meta.json` files, https://www.yandex.com/support/webmaster/en/indexnow/reference.md and `.../key.md`.

### 1.1 Endpoints (FAQ, "How Do I Submit a URL Using IndexNow?")
FAQ wording: "You may submit your request to only one of the following participating endpoints. Each endpoint sends your submission directly to its respective search engine, and your submission will be shared across all IndexNow-enabled search engines:"

| Engine | Endpoint (exactly as the FAQ lists it) | `meta.json` `api` value |
|---|---|---|
| IndexNow global | `https://api.indexnow.org/indexnow` | n/a |
| Amazon | `https://indexnow.amazonbot.amazon/indexnow` | (listed in searchengines.json as `amazonbot`; not fetched) |
| Bing | `https://www.bing.com/indexnow` | `https://www.bing.com/indexnow` |
| Naver | `https://searchadvisor.naver.com/indexnow` | `https://searchadvisor.naver.com/indexnow` |
| Seznam.cz | `https://search.seznam.cz/indexnow` | (listed; not fetched) |
| Yandex | `https://yandex.com/indexnow` | `https://yandex.com/indexnow` |
| Yep | `https://indexnow.yep.com/indexnow` | (listed; not fetched) |

`searchengines.json` also lists `internetarchive` (`https://web-static.archive.org/indexnow/meta.json`), which the FAQ endpoint list does not include. Not verified further.
Live probe (bare GET, no params): api.indexnow.org 400, www.bing.com 200, yandex.com 302, searchadvisor.naver.com 302. These only show the hosts answer; they are not submissions.

### 1.2 Does one ping reach all engines? YES (documented)
- FAQ: "your submission will be shared across all IndexNow-enabled search engines" and "You may submit your request to only one of the following participating endpoints."
- Documentation, "Requirement for search engines": "Search engines adopting the IndexNow protocol agree that submitted URLs will be automatically shared with all other participating search engines."
- Design consequence: ping ONE endpoint, `https://api.indexnow.org/indexnow`. Do not fan out to every engine. The `engines[]` array in `src/contract.ts` will normally have one entry. Fanning out to several is contrary to the FAQ wording and risks 429 (see 1.7).

### 1.3 Request formats
GET (one URL), documentation, "Submitting One URL":
`https://<searchengine>/indexnow?url=url-changed&key=your-key` ; optional `&keyLocation=...`.
"URL must be URL-escaped and encoded and please make sure that your URLs follow the RFC-3986 standard for URIs."

POST (set of URLs), documentation, "Submitting set of URLs":
```
POST /indexnow HTTP/1.1
Content-Type: application/json; charset=utf-8
Host: <searchengine>
{
  "host": "www.example.com",
  "key": "<key>",
  "keyLocation": "https://www.example.com/myIndexNowKey63638.txt",   // optional
  "urlList": ["https://www.example.com/url1", "https://www.example.com/folder/url2"]
}
```
- Max URLs: "You can submit up to 10,000 URLs per post, mixing http and https URLs if needed." (FAQ: "Submit no more than 10,000 URLs per request." and that exceeding it "may cause the request to fail or return an HTTP 422".) The suite's own cap of 100 is a stricter local choice; the protocol allows 10,000.
- FAQ POST example posts to `https://api.indexnow.org/indexnow`; "Use UTF-8 encoding and set the proper Content-Type header."
- Yandex's reference (https://www.yandex.com/support/webmaster/en/indexnow/reference.md) shows the identical body: `host`, `key`, optional `keyLocation`, `urlList`. `host` is required there; also states it supports GET and POST only (405 otherwise).

### 1.4 Key and key file rules
- Length and charset. FAQ: "Your key must be 8 to 128 characters long. Allowed characters: lowercase (a to z), uppercase (A to Z), numbers (0 to 9), and hyphens (-)." CAUTION: the Documentation page says "a minimum of 8 and a maximum of 128 hexadecimal characters" and then lists the wider set (a-zA-Z0-9-). The two pages disagree on "hexadecimal"; the list of allowed characters is the same everywhere (Yandex: "The key can contain characters a-z, A-Z, 0-9, -."). Use `^[A-Za-z0-9-]{8,128}$`.
- File. Documentation, Option 1: "You must host a UTF-8 encoded text key file {your-key}.txt listing the key in the file at the root directory of your website." Example: key `abcd1234` -> file `abcd1234.txt` with contents `abcd1234` (FAQ).
- FAQ: "Place the key file in the root directory of your site, or any publicly accessible folder on the same host (no login required)." Test: "If the file loads and displays only your key, your site is verified." "The text inside must exactly match your API key." Must be reachable "without login, firewall, or IP restrictions".
- Option 2 (`keyLocation`): "the location of a key file determines the set of URLs that can be included with this key. A key file located at http://example.com/catalog/key12457EDd.txt can include any URLs starting with http://example.com/catalog/ but cannot include URLs starting with http://example.com/help/." "It is strongly recommended that you use Option 1."
- Yandex key page adds: "Only UTF-8 encoding is supported", "The file must not contain HTML markup", "Yandex checks the key in every API request", "If your site has subdomains, use a separate key for each subdomain." FAQ agrees: "Each subdomain is treated as a separate host".
- Whitespace: whether a trailing newline in the key file is tolerated is NOT stated. Compare after `trim()`, but treat any other difference (extra text, HTML) as a mismatch.
- Documentation: "Only you and the search engines should know the key and your file key location." (Note the key file is by design publicly fetchable, so the key is not a secret from third parties who can read the site.)

### 1.5 Response codes
Documentation table ("Response format"), quoted:
| Code | Response | Reason |
|---|---|---|
| 200 | OK | URL submitted successfully |
| 202 | Accepted | URL received. IndexNow key validation pending. |
| 400 | Bad request | Invalid format |
| 403 | Forbidden | In case of key not valid (e.g. key not found, file found but key not in the file) |
| 422 | Unprocessable Entity | In case of URLs which don't belong to the host or the key is not matching the schema in the protocol |
| 429 | Too Many Requests | Too Many Requests (potential Spam) |

Notes: "The HTTP 200 response code only indicates that the search engine has received your URL." FAQ: first request may return 202 ("the search engine will verify your key before indexing the content"). FAQ 422 page adds "The same URL is being submitted repeatedly without meaningful changes." as a cause. Yandex adds 405 (method), and 422 for invalid key location / url / key length / charset / missing params. A submission is never a guarantee of indexing ("Submitting a URL does not guarantee immediate indexing.").
Design consequence: map 200 and 202 both to `submitted` (202 = accepted, key verification pending); 403 -> key rejected; 422 -> host/URL/key-schema mismatch; 429 -> back off.

### 1.6 Third-party submission
- Ownership is proven only by the key file being hosted on the host in the request (Documentation: "To submit URLs, you must 'prove' ownership of the host for which URLs are being submitted by hosting at least one text file within the host. Once you submit your URLs to search engines, search engines will crawl the key file to verify ownership").
- No page I read (documentation, FAQ, terms, Yandex reference) says who may send the HTTP request. NOT FOUND: any statement allowing or forbidding a third party to submit on behalf of a host. The protocol's only gate is the engine's own fetch of the key file. Our pre-flight (fetch `keyLocation`, require body == key) mirrors that gate and is consistent with the docs; it is stricter than the protocol, not required by it.
- FAQ lists CMS plugins and a CDN ("Cloudflare offers native IndexNow integration") as ways to submit, i.e. automation by a party other than the site owner is the normal pattern, but that is not an explicit third-party clause.

### 1.7 Rate and abuse guidance
- FAQ: "IndexNow does not publicly disclose exact rate limits, as each participating search engine sets its own daily submission thresholds per site." 429: "Pause submissions and retry after the time specified in the Retry-After header."
- "Wait at least 10 minutes before resubmitting the same URL, unless it has changed significantly." (429 section). Elsewhere: "wait at least 5 minutes between updates before resubmitting" (debounce section). The two numbers differ; the conservative 10 minutes was used here.
- "Submit only when content has changed. Do not resubmit unchanged URLs." "Submitting unnecessary updates may lead to wasted crawl quota without improving visibility." IndexNow is "not designed for submitting every URL on your site at once" (except after migration/redesign).
- Yandex: "There is no limit on the number of requests. You can adjust their frequency: Yandex uses algorithms that prevent sending too many requests." and "We don't recommend sending the same URL too often. If needed, send it at 10-minute intervals." Yandex 429 = "The number of requests for one IP address is exceeded." (per-IP: a public relay shares one egress IP across all callers).
- Design consequence: per-instance de-dupe of (host, url) for 10 minutes, honour `Retry-After`, no automatic retries.

### 1.8 Terms of use
https://www.indexnow.org/terms ("Terms of Service") is a contract between the user and the sponsors (Yandex N.V., Seznam.cz, a.s., Microsoft Corporation) governing use of the indexnow.org website; the specification is licensed CC BY-SA 4.0. It contains no clause about submitting URLs, relays, or automation. It reserves the right to change the protocol: "make changes that result in your existing IndexNow files becoming non-compliant with the revised protocol", and "no Sponsor shall obligated to index, read or otherwise make use of any sitemap published by you". Per-engine terms: see COMPLIANCE.md.

## 2. Google PageSpeed Insights API v5

Sources: https://developers.google.com/speed/docs/insights/v5/get-started, https://developers.google.com/speed/docs/insights/v5/reference/pagespeedapi/runpagespeed, live discovery doc `https://pagespeedonline.googleapis.com/$discovery/rest?version=v5`, live API call, Lighthouse source `GoogleChrome/lighthouse` `core/audits/`.

### 2.1 Endpoint and parameters
- `GET https://www.googleapis.com/pagespeedonline/v5/runPagespeed`
- `url` (required): "The URL to fetch and analyze".
- `strategy`: "The analysis strategy (desktop or mobile) to use, and desktop is the default". Discovery enum: `STRATEGY_UNSPECIFIED, DESKTOP, MOBILE`.
- `category` (repeatable): "A Lighthouse category to run; if none are given, only Performance category will be run". Discovery enum: `CATEGORY_UNSPECIFIED, ACCESSIBILITY, BEST_PRACTICES, PERFORMANCE, PWA, SEO, AGENTIC_BROWSING`. To get the SEO score you must send `category=seo` (and `category=performance` to keep performance): `...?url=<enc>&strategy=mobile&category=performance&category=seo&key=<KEY>`.
- Other params: `locale`, `utm_campaign`, `utm_source`, `captchaToken`.
- `key=yourAPIKey`: "The API key is safe for embedding in URLs; it doesn't need any encoding."

### 2.2 Is a key required? Docs say no; live behaviour says keyless is dead
- Docs: "The API can be used with or without an API key, although a key is recommended for frequent, automated queries."
- LIVE TEST 2026-10-27 (two keyless calls, `url=https://example.com/`): both returned HTTP 429 `RESOURCE_EXHAUSTED`: "Quota exceeded for quota metric 'Queries' and limit 'Queries per day' of service 'pagespeedonline.googleapis.com' for consumer 'project_number:583797351490'." with `"quota_limit": "defaultPerDayPerProject"` and `"quota_limit_value": "0"`.
  Meaning: keyless calls are billed to a shared default Google project whose daily quota is 0 right now. Design: treat PSI as requiring `PAGESPEED_API_KEY`; the existing "skipped when key not set" behaviour is correct and a keyless attempt would fail. (Observed from one network at one time; the docs wording has not changed.)
- Quota numbers: NOT FOUND on any official Google docs page I could read (the quota page `.../v5/rate-limits` is a 404). Third-party pages and a search summary cite 25,000 queries/day and 400 queries per 100 seconds per project as defaults; I did NOT verify these against the Google Cloud Console. Treat as unverified; read them in the Cloud Console (APIs & Services > PageSpeed Insights API > Quotas) for the project that owns the key.

### 2.3 Response paths
Top-level: `captchaResult`, `kind`, `id`, `loadingExperience`, `originLoadingExperience`, `lighthouseResult`, `analysisUTCTimestamp`. Docs flag: "We plan to discontinue including real-world data from the Chrome User Experience Report in this API." Do not rely on `loadingExperience`.

| Metric | JSON path | Unit / notes |
|---|---|---|
| Performance score | `lighthouseResult.categories.performance.score` | 0..1 (docs sample: `0.96`); multiply by 100 for display. Can be null if the category errored. |
| SEO score | `lighthouseResult.categories.seo.score` | only present if `category=seo` was requested |
| LCP | `lighthouseResult.audits["largest-contentful-paint"].numericValue` | ms (`numericUnit: millisecond`, Lighthouse source) |
| CLS | `lighthouseResult.audits["cumulative-layout-shift"].numericValue` | unitless (`numericUnit: unitless`) |
| TBT | `lighthouseResult.audits["total-blocking-time"].numericValue` | ms |
| TTFB | `lighthouseResult.audits["server-response-time"].numericValue` | ms ("Initial server response time"); this is Lighthouse's server response time audit, not a field named TTFB |

Audit ids and `numericUnit` confirmed in Lighthouse `main` source (`core/audits/metrics/largest-contentful-paint.js`, `.../cumulative-layout-shift.js`, `.../total-blocking-time.js`, `core/audits/server-response-time.js`). PSI runs a specific Lighthouse build (`lighthouseResult.lighthouseVersion`), so any audit can be absent or have `numericValue` undefined: map missing to `undefined`, never to 0.
Other useful fields: `lighthouseResult.finalUrl`, `lighthouseResult.runWarnings[]`, `lighthouseResult.configSettings.emulatedFormFactor`.

### 2.4 Terms
The PSI docs pages link only "Google Developers Site Policies". The governing document is the Google APIs Terms of Service (https://developers.google.com/terms, "Last modified: November 9, 2021"). Quotes and relay implications in COMPLIANCE.md.

## 3. Cloudflare GraphQL Analytics

Sources: https://developers.cloudflare.com/analytics/graphql-api/limits/ (updated 2026-10-02), `.../features/data-sets/`, `.../features/discovery/settings/`, https://developers.cloudflare.com/ai-crawl-control/reference/graphql-api/, https://developers.cloudflare.com/fundamentals/api/reference/permissions/ (updated 2026-10-12), plus LIVE schema introspection through the Cloudflare API MCP on 2026-10-27 (account zones `tatinc.us`, `mashcribs.com`, both "Free Website").

Endpoint: `POST https://api.cloudflare.com/client/v4/graphql`, header `Authorization: Bearer <API_TOKEN>`, `Content-Type: application/json`, body `{"query": "...", "variables": {...}}` (shape from the Cloudflare tutorial https://developers.cloudflare.com/analytics/graphql-api/tutorials/end-customer-analytics/).

### 3.1 Token permission
- Zone-scoped queries (`viewer.zones(filter:{zoneTag})`): permission "Analytics Read" in the "Zone permissions" list ("Grants read access to analytics"); in the token UI that is Zone > Analytics > Read. LIVE confirmation: a token without it got `GraphQL error: Actor '...' does not have permission 'com.cloudflare.api.account.zone.analytics.read' for zone <id>`.
- Account-scoped queries: "Account Analytics Read" (the Cloudflare token walkthrough says: "select Account in the first drop-down list, Account Analytics from the second drop-down list, and Read from the third").
- Use zone scope for this tool. The token should be scoped to the one zone.

### 3.2 Which dataset gives requests / bytes / uniques
Live schema (introspection, 2026-10-27):
- `httpRequests1dGroups` (zone): `sum { requests bytes ... }`, `uniq { uniques }`, `dimensions { date }`, args `filter`, `limit`, `orderBy`; filter uses `date_geq` / `date_leq` (a Date, not datetime). This is the only dataset with `uniq.uniques` (unique IPs; docs: "uniq { uniques } # unique IPs").
- `httpRequestsAdaptiveGroups` (zone): `count` (requests), `sum { edgeResponseBytes visits ... }`, `avg`, `quantiles`, `dimensions { datetime* userAgent userAgentBrowser userAgentOS verifiedBotCategory botDetectionIds botScore clientRequestHTTPHost clientRequestPath edgeResponseStatus requestSource ... }`. NO `uniq` type (introspection returned null for `ZoneHttpRequestsAdaptiveGroupsUniq`). Cloudflare's migration guide: "unique visitors per colocation is not supported in httpRequestsAdaptiveGroups ... does support visits".
- Other zone nodes present: `httpRequests1hGroups`, `httpRequests1mGroups`, `httpRequestsAdaptive`, `httpRequestsOverviewAdaptiveGroups`.
- Sampling: Adaptive datasets are sampled ("Cloudflare almost always uses adaptive sampling ... If the number of records is relatively small, sampling is not used"); counts are estimates. State this in the result `message`; the contract has no field for it.

### 3.3 Plan availability and time ranges
- Official: "Although we allow access to ALL plans for the essential datasets (like httpRequestsAdaptiveGroups, firewallEventsAdaptive, etc), users on larger plans benefit from an extended set of datasets and wider query limits." and "Adaptive datasets, such as httpRequestsAdaptiveGroups and firewallEventsAdaptive, retain at least 31 days of data on every plan. Aggregated datasets, such as httpRequests1hGroups, keep their own per-plan limits."
- `httpRequests1dGroups` plan availability and max range: NOT FOUND in official docs. The per-plan numbers are exposed at runtime by the `settings` node (`enabled`, `availableFields`, `maxPageSize`, `maxNumberOfFields`, `notOlderThan` (seconds), `maxDuration` (seconds)). I could not run it: the MCP token lacks Analytics Read and the operator's general Cloudflare token; not investigated further). Recommendation: the tool should read `settings` for the dataset it uses and report `windowStart/windowEnd` clamped to `maxDuration`/`notOlderThan`, rather than hardcoding plan numbers. A third-party MCP README claims `httpRequestsAdaptiveGroups` rejects windows over 1 day on standard plans: unverified, so default to a 24 h window.
- Rate limit: "The default quota is 300 GraphQL queries over 5-minute window". Per-request limits: "A zone-scoped query can include up to 10 zones".
- Bot breakdown (AI Crawl Control GraphQL page): `userAgent_like: "%...%"` "Can be spoofed", All plans; `requestSource: "eyeball"` All plans; `clientRefererHost_like` "Paid plans only"; `botDetectionIds_hasany: [...]` "Reliably verified by Cloudflare", requires Bot Management. `verifiedBotCategory` exists as a dimension and filter field (live schema); the official pages I read give no plan table for it: NOT FOUND, so check `settings.httpRequestsAdaptiveGroups.availableFields` at runtime. The same page documents detection ids in a comment: 123815556 = GPTBot, 132995013 = ChatGPT-User, 126255384 = OAI-SearchBot.
- Design consequence: on a Free zone, count AI bots by `userAgent_like` substring and label the numbers "by user-agent string, can be spoofed". Do not call them verified.

### 3.4 Working example queries
Field names, filter names and types below were checked against the live schema by introspection. They were NOT executed (no token with Analytics Read was available), so run them once with a real token before trusting the response shape. Variables: `zoneTag` (string), `from`/`to`.

1. Requests, bytes, uniques per day (aggregated, not sampled):
```graphql
query ($zoneTag: string, $from: Date, $to: Date) {
  viewer { zones(filter: { zoneTag: $zoneTag }) {
    httpRequests1dGroups(limit: 31, filter: { date_geq: $from, date_leq: $to }, orderBy: [date_ASC]) {
      dimensions { date }
      sum { requests bytes }
      uniq { uniques }
    }
  } }
}
```
2. Requests and bytes for a time window (adaptive; use when a datetime window is needed):
```graphql
query ($zoneTag: string, $from: Time, $to: Time) {
  viewer { zones(filter: { zoneTag: $zoneTag }) {
    httpRequestsAdaptiveGroups(limit: 1, filter: { datetime_geq: $from, datetime_lt: $to, requestSource: "eyeball" }) {
      count
      sum { edgeResponseBytes visits }
    }
  } }
}
```
3. AI-crawler requests by user-agent (adaptive; pattern from the AI Crawl Control page):
```graphql
query ($zoneTag: string, $from: Time, $to: Time) {
  viewer { zones(filter: { zoneTag: $zoneTag }) {
    httpRequestsAdaptiveGroups(
      limit: 100, orderBy: [count_DESC],
      filter: { datetime_geq: $from, datetime_lt: $to, requestSource: "eyeball", userAgent_like: "%GPTBot%" }
    ) {
      count
      dimensions { userAgent verifiedBotCategory }
      sum { edgeResponseBytes }
    }
  } }
}
```
`userAgent_like` takes one pattern; for several bots either issue one query per bot or use the schema's `OR: [{userAgent_like: ...}, ...]` (the AI Crawl Control page shows `OR: [...]` for referrer hosts).
4. Runtime limits for the zone:
```graphql
query ($zoneTag: string) {
  viewer { zones(filter: { zoneTag: $zoneTag }) {
    settings {
      httpRequests1dGroups { enabled notOlderThan maxDuration maxPageSize }
      httpRequestsAdaptiveGroups { enabled availableFields notOlderThan maxDuration maxPageSize }
    }
  } }
}
```

### llms.txt (https://llmstxt.org/, now "v2")
Quoted from the proposal: "The llms.txt file spec is for files named llms.txt, at the root path /llms.txt of a website or at any subpath (e.g. /docs/llms.txt). A file covers the URLs under its path... A file following the spec contains the following sections as markdown, in the specific order:
1. An optional byte-order mark (BOM)
2. An H1 with the name of the project or site. This is the only required section
3. A blockquote with a short summary of the project, containing key information necessary for understanding the rest of the file
4. Zero or more markdown sections (e.g. paragraphs, lists, etc) of any type except headings, containing more detailed information about the project and how to interpret the provided files
5. Zero or more markdown sections delimited by H2 headers, containing 'file lists' of URLs where further detail is available
Each 'file list' is a markdown list, containing a required markdown hyperlink [name](url), then optionally a : and notes about the file."
"The 'Optional' section is used, by convention, for secondary information: links an agent can skip when a shorter context is needed."
Valid minimal file:
```
# Site name
> One-sentence summary taken from the page's meta description.

## Pages
- [Home](https://example.com/): what it is
## Optional
- [About](https://example.com/about)
```
Also proposed (not required): a `.md` twin of pages (`page.html.md` or `page.md`), and `Link: </docs/llms.txt>; rel="describedby"`. The page says llms.txt is "mainly useful for inference rather than training". Not an official standard body spec; it is a proposal by Answer.AI. Drafting rule for this suite: only H1 (page title), blockquote (meta description), and links to URLs actually observed (the page, sitemap, canonical).

## 5. mcp-use 2.x views (installed 2.11.2)

Sources: installed package `node_modules/mcp-use` (README.md, `dist/tools.d.ts`, `dist/views/*.d.ts`, `dist/react/**/*.d.ts`, `dist/response-helpers.d.ts`, `mcp-use build --help`), https://docs.mcp-use.com/v2/typescript/mcp-apps.md, `.../mcp-apps/interactivity.md`, `.../mcp-apps/content-security-policy.md`, `.../mcp-apps/quickstart.md`. Installed package and v2 docs agree. The v1-era docs (`useWidget`, `resources/`) are the OLD API.

### 5.1 Terminology differs from the old docs
- v2 calls them Views. There is NO `useWidget` export and no `resources/` directory convention. `react/index.d.ts` exports: `useToolContext`, `useCallTool`, `useDynamicTool`, `useSendFollowUp`, `useOpenExternal`, `useDisplayMode`, `useHostContext`, `useViewState`, `useViewTool`, `useFiles`, `useDeepLink`, `useModelContext`, `useViewTheme`, `useSendSizeChanged`, `ThemeProvider`, `ViewControls`, `Image`, `ModelContext`, `ErrorBoundary`, `ToolError`, `ToolCancelledError`.
- The `widget()` response helper still exists in `mcp-use` but is `@deprecated`: "Prefer returning a plain CallToolResult from a tool registered with `view: { name }`. Put view props in `structuredContent` and model-facing text in `content`."

### 5.2 Directory and binding convention
- `views/<view-name>/view.tsx` (default export = a React component that takes no props). The `view.name` in the tool definition "must match a directory under views/". This repo already has `views/render-submission-canvas/view.tsx` (+ `Canvas.tsx`, `lib.ts`).
- The view-bound tool MUST declare an `outputSchema` (the view reads `structuredContent`). "A view may have at most one bound tool"; a second tool naming the same view is rejected.
- Optional named export `viewConfig` in `view.tsx`: `{ autoResize?: boolean (default true), displayModes?: ("inline"|"fullscreen"|"pip")[] (must include "inline"), preferredDisplayMode?: "inline"|"fullscreen" }`.
- `mcp-env.d.ts` (generated, "Do not edit") registers `typeof import("./index.js")` so `useCallTool("tool-name")` is typed; tool refs must be exported from `index.ts` (`export const x = server.tool(...)`), which `submitBraveUrl` already is. Tools created otherwise use `useDynamicTool<Args, Result>("name")`, which is what the existing view uses.

### 5.3 Minimal working example (adapted from the installed README)
```ts
// index.ts
export const auditSite = server.tool(
  { name: "render-submission-canvas", title: "...", inputSchema: z.object({...}), outputSchema: canvasPropsSchema,
    view: { name: "render-submission-canvas", description: "...", csp: { connectDomains: [] }, prefersBorder: true },
    annotations: { readOnlyHint: true, destructiveHint: false, openWorldHint: false } },
  async (args) => ({ content: [{ type: "text", text: "Opened the canvas." }], structuredContent: props }),
);
```
```tsx
// views/render-submission-canvas/view.tsx
import { useToolContext, useCallTool } from "mcp-use/react";
export default function View() {
  const ctx = useToolContext();            // status: "pending" | "ready" | "error"
  const audit = useCallTool("audit-site"); // { callTool, data, error, isPending }
  if (ctx.status === "pending") return <p>Loading...</p>;
  if (ctx.status === "error") return <p>{ctx.error.message}</p>;
  return <button onClick={() => void audit.callTool({ targetUrl: "https://example.com" })}>Audit</button>;
}
```
Props arrive as the tool's `structuredContent`: `ctx.toolOutput` once `status === "ready"` (while pending, `ctx.toolInput` holds partial arguments). `useToolContext` latches the FIRST structured result for the view's life.

### 5.4 How a view calls other tools
- `useCallTool("name")` (or `useCallTool(toolRef)`, or `useDynamicTool<Args,Result>("name")`) returns `{ callTool(args), data, error, isPending }`. `callTool` resolves for every non-error result and "rejects when the tool returns an error or the request fails" with `ToolError` (which carries `.result`, so a tool that returns `isError: true` plus `structuredContent` can still be unwrapped; the existing view already does this). Transport/capability failures reject with a plain `Error`; the `.d.ts` mentions a missing `serverTools` host capability as one such failure, i.e. a host may refuse to proxy tool calls from a view. Test in Claude and ChatGPT hosts, not only the Inspector.
- A tool that should be callable by the view but hidden from the model: `visibility: "app"` on the tool definition ("`app` marks app-private helper tools callable from views via `useCallTool` while the host hides them from the model"). Default is visible to both. Relevant for the discovery tools if they should not be model-callable (probably they SHOULD stay model-callable).
- Other host actions: `useSendFollowUp()` (needs host `message` capability), `useOpenExternal()` (needs `openLinks`), `useDisplayMode()`, `useFiles()`.

### 5.5 Build and serving
- `mcp-use build` -> `.mcp-use/build`. Options: `--inline` ("Embed view JavaScript and CSS in MCP resources"), `--views-dir`, `--mcp-dir`, `--entry`, `--source-maps`, `--no-views-config`. `package.json` already maps `build`, `start`, `dev`.
- Production views are served from `${basePath}/_mcp-use/views/<name>/` (assets under `.mcp-use/build/views/<name>/`, `assets/...`); `MCP_ASSETS_URL` rewrites these to absolute URLs at build time. The resource MIME type is `text/html;profile=mcp-app`, resource URI `ui://...` (`viewResourceUri(name)`), extension id `io.modelcontextprotocol/ui`.
- `tsconfig.json` `include` lists `index.ts`, `mcp-env.d.ts`, `src/**/*`, `test/**/*`, `.mcp-use/**/*.d.ts` and NOT `views/**`; I did not check whether `mcp-use typecheck` covers views separately.

### 5.6 CSP and props
- `view.csp` on the bound tool (type `McpUiResourceCsp`): `connectDomains`, `resourceDomains`, `frameDomains`, `baseUriDomains`. Merge order (high to low): author `view.csp`; `CSP_*_DOMAINS` env vars / `CSP_URLS`; framework auto-append (`MCP_URL` -> connectDomains; assets origin -> resourceDomains).
- `view.permissions` (sandbox permissions), `view.domain` (dedicated UI origin; for Claude the SDK hashes the full MCP endpoint into `*.claudemcpcontent.com`), `view.prefersBorder`, `view.description`, `view.entrypoints` (ChatGPT launchers).
- Set `MCP_URL` to the public origin in the deployed environment so CSP and view domains resolve (docs: "Without a valid MCP_URL, View reads use the request path and query with the forwarded origin"). Since the canvas only calls tools through the host bridge, it needs no `connectDomains` of its own; add none unless the view fetches directly.
- Props contract: `structuredContent` must satisfy the tool's `outputSchema` (server rejects non-error results lacking it). Hosts receive it as `toolOutput` in the view.
